官方没说的六件事

大部分对账工具悄悄算错，根子都在这几个地方。直接摊开讲：

缺口后果
transaction-type 没有官方枚举。网上流传的 Order / Refund / Transfer / Liquidations 找不到亚马逊出处。硬编码这四个的工具，遇到没见过的值会静默丢行。这个工具不做归类，全部原样列出。
amount-type 和 amount-description 也没有官方枚举。新费用代码随时会出现，硬编码的映射表会悄悄过期。
没有说明正负号规则。费用是不是负数，只能靠推断。
没有说明文件编码。SKU 或商品名里有非 ASCII 字符时可能乱码。
没有说明汇总行结构。实测首行只有 settlement-id、日期、total-amount 和 currency。当成数据行读进去，总额会被重复计一遍。
24 个列全都没给数据类型和可空性。解析器只能靠猜。

对不上的五个具体原因

一、储备金漏了

amount-type = other-transaction 下面有 Current Reserve Amount 和 Previous Reserve Amount Balance。亚马逊压一部分钱，下期再放。只算「订单收入减费用」不算这块，总数永远等不上打款金额。这是最常被漏掉的一项。

二、posted-date 落在结算周期外

posted-date 是单笔实际发生的时间，结算是按 settlement-start-date → settlement-end-date 切的。这两个不一定重合，跨月的时候基本都不重合。ERP 按发生日归集、亚马逊按周期结算，那是两套口径，不是数据出错。汇总按结算周期来。

三、一个订单在报告里是好几行

同一个 order-id 会拆成多行——Principal 一行、Commission 一行、FBA 费一行。要归到 SKU，得按 order-id 加上 order-item-code。光按 order-id，一单买了两个不同东西就串成一个了。

四、quantity-purchased 是重复的，不是每行独立的

quantity-purchased 在同属一个订单项的每一行上都会重写一遍。直接把这一列加起来，等于把数量乘以行数。要先按 order-id + order-item-code 去重。这个坑特别阴，因为它不报错，只是给你一个看起来很合理的错数——我自己写这个工具的时候就翻过一次车。

五、把不同币种加到一起了

Flat File V2 只有一个 currency 列，没有汇率列。不同币种的结算不能相加，得按币种分开。
